fix: a send point nobody passed, four events nobody emitted, a worker nobody enqueued

A third sweep, prompted by §13.4 — the commit that emptied the orphan-table
gate's escape hatch had introduced an orphan WORKER, which that gate could not
see because a worker is not a table. So this asks the general question: the
orphan sweep catches one KIND of declaration going unread; what are the others?

Four kinds swept — workers, event types, send points, columns. Two clean, two
not, and one of them is the largest single finding of the programme. §14 of
doc/SMART_MAIL_PR2_PR5_QC_AUDIT.md has the detail.

The send-point binding layer was completely inert
-------------------------------------------------
`mail_send_point` carries 22 rows. `sendpoint.service.resolve` implements the
whole tiered lookup — a binding for this send point AND this corporate entity,
then tenant-wide, then the legacy section, then the purpose identity.
`email.service.resolveMail` accepts a sendPoint and asks the registry first. The
console lets a tenant bind an identity to every row. The client API exists.

NO CALLER IN src/ EVER PASSED ONE. A repo-wide scan for a literal `sendPoint:`
value outside the mail composer's own "user.compose" default returned nothing.
Every system-email caller passed `purpose: "NOTIFICATIONS"` and stopped, so
tiers 1 and 2 — the two the feature exists for — were unreachable.

Nine rows declared is_wired = true, above a comment reading "the eight true rows
below were read off the code, not guessed", naming the exact files. They did not
do it.

This is worse than an orphan table. A table nobody reads is invisible; this
actively invited the configuration, recorded the tenant's choice and ignored it,
with no symptom — mail still went out, from a plausible address. Somebody
routing Sign-in code to security@ and Document sent to a party to documents@ got
neither.

Eight are now passed at their call sites; email-send.js carries the key through
Redis so campaign and scheduled-report sends resolve it in the worker (and
resolve it THERE rather than at enqueue, so a binding changed while a job waits
is honoured); document.share passes entityId so a group sends each company's
paperwork from that company's address.

Safe to ship live: tiers 3 and 4 are byte-for-byte what email.service already
did, so a tenant who has bound nothing sends from precisely the address they
sent from yesterday. Passing a key can only ADD an answer above the existing
ones.

The ninth, auth.otp, claims a sender that does not exist — 2FA is TOTP through
an authenticator app and every other "one-time" there is a one-time LINK. 10773
flips it to is_wired = false rather than deleting the row: the row is still
where the binding belongs the day an emailed code exists, and deleting it would
silently drop any binding a tenant has already made.

Four event types were seeded, described, and emitted by nothing
---------------------------------------------------------------
Each ships with an English and a French description that appears in the tenant's
event catalogue and in the notification-rule builder. A key an administrator can
select that never fires is a rule that silently never runs.

  email.thread.replied   the ingest ternary emitted `email.thread.created` on
                         one branch and the pre-thread engine's `email.received`
                         on the other — two keys for one moment, and the one in
                         the rule builder was the one that never fired. Now
                         symmetric on the thread grain. `categoryFor` keys on
                         the domain, so notification routing is unchanged.
  email.attachment.filed filing emitted only `document.captured`. Now both:
                         one says a document exists on a record (what the vault
                         listens to), the other says an inbound attachment was
                         classified and a human confirmed it.
  email.draft.saved      now once per draft, on creation — what 10739's own
                         description promises. Per-save would bury the log under
                         one conversation's typing.
  document.share         a send point, not an event. See above.

ai-vision was a worker for a screen that was never built
--------------------------------------------------------
Registered in workers.js, enqueued by nothing. It fed a document-scan turn to
the assistant, and the assistant has no image entry point: no route, no
validator, no upload control. No job could ever have reached it. Removed rather
than left behind an escape hatch — services/ai/vision.service is untouched and
has three live callers, including mail's attachment extraction, which is
doc-vision delivered somewhere a person can actually reach it.

scheduled-report is also enqueued by nothing in-app, and that one is by design:
its handler names an external cron or POST /reports/scheduled/run-due, and both
exist. Listed as externally driven, with a ceiling on the list. Worth a decision
— it is the only periodic job not in scheduleRecurring().

Two classes came back clean
---------------------------
All 141 columns the mail migrations add are read. And §12.4's signature-cache
fix did land, via deleteAllIdentityCached rather than the narrower helper the
audit named — the behaviour is right, only the unused helper remains.

Gates
-----
orphan-wiring-sweep asks the general question: every registered worker must have
a producer, every seeded event type must be emitted. mail-send-point-wiring
holds the registry to its own is_wired claim and refuses a bare mention of a key
as evidence — it guards itself with a row that is named in prose and sent by
nothing. Four sweeps now stand, one per kind of declaration, each with a named
size-capped allowance list, because an allowance that grows is the gate being
routed around.

5,091 tests across 332 suites, 0 lint errors, column/idempotency/citext OK.
