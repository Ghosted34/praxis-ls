The finding, in one paragraph

The merged programme had every table, column and pure helper the engineering guide asks for, and the build was green — but eleven of its tables were read by zero lines of application code, its feature flags gated nothing, and no LLM call was made on any path. A test that imports a module and calls it has tested that module; it has not tested that the product uses it. That is the whole defect class, and four sweeps found it in six different shapes.

All six are now closed and each has a standing gate that fails the build if it recurs. Nothing below is a code blocker. Deploy applies the migrations and projects the features on its own; CI's migrations job runs them against a real Postgres. What is genuinely left is five commercial and operational calls, and one round of switching AI on per tenant.

Before any of this is reachable

6 items

In order. Each one is a hard stop for everything below it — requireFeature is mounted in front of every mail router by the module loader and has no bypass, not even for the CEO, who bypasses RBAC. The first two are automatic — traced through the deploy path after this report was first written, and corrected here.

OPS-1Deploy does it

The migrations and the seed

Four new files: 10771 (the mail_ai AI flag), 10772 (mail.ocr, off), 10773 (marks the auth.otp send point unwired) and the platform seed 9114_seed_mail_features.sql — the switch that makes any of it reachable.

deploy.sh runs docker compose run --rm migrate, whose command is npm run db:migrate:platform && npm run db:migrate:tenants. migratePlatform() applies m.files.platformSeeds() under scope platform-seed, tracked by filename — so the seed lands on its own, with no separate step.

OPS-2Deploy does it

Re-projecting existing tenants

Also automatic, and for a less obvious reason: migrateTenant() calls projectFeatures(slug) immediately after applying the tenant files, and db:migrate:tenants runs it for every tenant in the fleet. So the same deploy that adds the catalogue rows projects them into every existing tenant's feature_state.

To confirm rather than assume node scripts/tenant/feature-report.js --slug=<slug> after the deploy. If a tenant is missing the mail.* rows, that is the diagnostic, and provisioning.projectFeatures(slug) is the manual re-run.
OPS-3Watch this

ai.assistant.backend must be on first

It is declared in mail.ai's depends_on. Projection forces a feature off when a dependency is off, applied to a fixpoint, and treats an unknown dependency as unmet.

The trap Switching mail.ai on with the backend off leaves it off, silently and correctly. This is §3.3's rule — an AI flag is a floor, not a ceiling — moved out of the service layer and into the projection, so it now fails in a place an operator can see rather than only at request time.
OPS-4Per tenant

Opt into mail.ai and mail.ocr

Both ship off by design, not because they are unfinished. mail.ai is opt-in like every other ai.* key; mail.ocr sends a scanned supplier invoice — bank details and all — to a vision vendor and is billed per page, which a tenant should agree to separately from drafting.

OPS-5Watch this

ai.vectorization for semantic search

Without it, threads are never embedded. Search then returns nothing and raises no error, which reads as a broken feature rather than an unconfigured one. Every vector hit is re-filtered through visibility.clause on the way out, so an unbound thread cannot leak through search.

OPS-6Ops

Vendor credentials in the platform store

Chat (deepseek / gemini) and vision (gemini). Every generating path runs the same five steps in fixed order — gate, ground, generate, fence, meter — and metering happens in a finally, on success and on failure, so a vendor outage still bills the attempt rather than losing the record of it.

Yours to call

5 decisions

Each of these has a working default in the branch. None is load-bearing on the code — changing any one is an edit to a seed file or an env var. They are here because I picked them and you may not agree.

DEC-1Commercial

What Starter gets

I gave Starter a working mailbox and nothing that costs a vendor call or implies a team: mail.core, mail.composer, mail.binding, mail.signatures, mail.deliverability. Full and Enterprise get all fifteen.

How I drew the line comms and signatures are already in Starter, so a mailbox is consistent with what that plan promises today. The shared inbox, the immutable archive and the AI are what the larger plans are for. This is a pricing judgement wearing a SQL file — overrule it freely.
  • In branchThe five above. A real mailbox bound to real records, nothing that costs a vendor call or implies a team. Upgrade pressure comes from the shared inbox.
  • LeanerDrop mail.binding — core, composer, signatures, deliverability only. Starter becomes a plain mailbox and the ERP hook is the thing you upgrade for. Strongest upgrade pressure; weakest demo.
  • FullerAdd mail.followup and mail.secure_links. Neither costs anything per use and both demo well. Buys adoption, spends the upgrade lever.
DEC-2Policy

Twelve keys default on, three default off

Following 9110's stated rule that default_state answers "is this module shippable?", not "did the customer buy it?" — plan inclusion is plan_feature's job and per-tenant exceptions are tenant_feature_override's. The three off are mail.ai, mail.ocr and mail.provider.oauth, none for readiness reasons.

  • In branch12 on / 3 off. default_state answers "is it shippable", plan_feature answers "did they buy it", tenant_feature_override handles the exceptions. Three concepts, each doing one job.
  • QuieterAlso default mail.antispoof and mail.archive off, flip them once the first tenant has run clean for a week. Costs a second deliberate flip per tenant, and those two are the compliance story.
  • SimplestAll fifteen on; let plan and override do 100% of the gating. One fewer concept — but every Full-plan tenant gets AI billing exposure the day the catalogue lands.
DEC-3Load

SCHEDULED_REPORT_CRON defaults to hourly

"5 * * * *". Scheduled reports had been waiting on a cron nobody had written down; the new scheduler fans out across every live tenant on the hour, with jobId: schedreport:<db>:live-<hourStamp> and attempts: 1.

Worth a look before scale Two things move together here: fan-out cost, and how late a report can be. Hourly means a report scheduled for 14:30 goes out at 15:05. The value is an env var, so any of these costs nothing to adopt.
  • In branch5 * * * * — hourly, every live tenant. Worst-case lateness 60 min; 24 fan-outs a day.
  • Cheaper5 6-19 * * * — waking hours only. Halves the fan-out and stops generating overnight reports nobody reads. A report scheduled for 02:00 waits until 06:05.
  • Tighter5,20,35,50 * * * * — worst-case lateness drops to 15 min at 4× the fan-out. Only worth it if report schedules are actually sub-hourly.
DEC-4Timing

When mail.provider.oauth gets switched on

Microsoft Graph and Gmail are built and deliberately gated — the call was one provider done properly first, and the one the first tenant runs is cPanel IMAP/SMTP. Nothing technical is waiting on this; it needs a date.

  • In branchStays off. Revisit once the first cPanel tenant has run clean. Zero risk, zero progress — Graph has never touched a real mailbox.
  • PilotOne tenant via tenant_feature_override, catalogue default unchanged. Tests OAuth against a real mailbox without committing the fleet. My pick if you want movement.
  • Ship itDefault on next release, plan gates it. Only with an owner for the Microsoft and Google app registrations and consent screens — that review, not the code, is the long pole.
DEC-5Product

Whether auth.otp should ever exist

The send-point registry claimed is_wired = true for nine points no caller passed. Eight of them are now genuinely wired. The ninth, auth.otp, has no caller because 2FA is TOTP and there is no emailed code anywhere in the product — so 10773 marks it unwired rather than inventing one.

If an emailed OTP is planned That row becomes a claim waiting to be made true rather than a false one, and the wiring gate will hold you to it the moment you flip it back.
  • In branchis_wired = false. The registry tells the truth and the gate stays green. Leaves a row describing a thing that does not exist.
  • Delete itDrop the row entirely. Cleanest if an emailed OTP is never coming — nothing false, nothing to explain to the next reader. Costs one more migration.
  • Build itImplement the emailed code and flip the row back. The usual reason this comes up is that TOTP-only 2FA locks out anyone without the authenticator app. If that has bitten support, this is the answer.

UNV-1CI closes it

No database was available at any point in this work

Not once, in any of the four sweeps. Every database gate that passed — db:check:idempotency, db:check:columns, check-citext-arrays, the catalogue-coverage and dependency-cycle checks — is static analysis over migration text. It reads SQL; it does not run it. The migrations in this branch have never been applied to a live database, and neither has the seed.

But CI can settle it, and does. The migrations job in ci.yaml stands up a real pgvector/pgvector:pg16 service, runs migrate-platform.js — which is what applies the seed — provisions a tenant from nothing, and re-applies the whole tenant set to prove the ledger reports zero. Push the branch and that is no longer an assumption.

What CI still will not tell you It proves the SQL applies and is idempotent on an empty database. It does not prove projection behaves against your existing tenants' current feature_state. So the one thing worth doing by hand afterwards is feature-report.js --slug=<a real tenant>.
UNV-2Closed

Client lint had never run — and it was red

The root eslint.config.js ignores client/**, so client lint sits outside the backend gate entirely and nothing in this programme had ever run it. Pulled the real config into a container and ran it: one error and 115 warnings against a --max-warnings 112 budget. Both were this branch's.

The error was real. useGuardrails declared [enabled, key] while its body closed over four values not in that array. The array was the correct part — to and attachments are new references every render, so listing them restarts the 600 ms debounce on every keystroke and the check never fires. The body was wrong: it sent whatever the closure captured rather than what was on screen. Latest inputs now go through a ref, so the array is honest rather than suppressed.

And the three surplus warnings All react-refresh/only-export-components, on files this branch added. 53 files already carry that rule — but a --max-warnings number is a ratchet: it exists so the count comes down, not so new work can spend the headroom old work left behind. useGuardrails and schedulePayload moved into their own modules, which is the better shape anyway: every consumer already imported them directly and nothing ever took them from the barrel. Now 0 errors, 111 warnings.
