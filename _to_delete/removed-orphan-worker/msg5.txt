feat(mail): the switch that turns it on, and the screens PR-5 never got

Two things were still true after the third sweep: the whole programme was
unreachable, and a quarter of its API had no interface. §15 of the audit has the
detail.

There was no way to turn any of it on
--------------------------------------
Migration 10730 seeds fifteen mail.* rows into every tenant's feature_state, all
'off'. Every mail surface is gated on them, and requireFeature is mounted in
FRONT of each router by module-loader.js with no bypass — not even for the CEO,
who bypasses RBAC.

NONE of those keys existed in platform.feature_catalogue.

provisioning.projectFeatures() iterates the CATALOGUE, so it never touched them.
plans.service.reprojectPlan does the same. No tenant-side route writes
feature_state at all. So there was no supported way to switch the mailbox on —
not from the console, not from a plan, not from a tenant screen. Four commits of
work sat behind a hard 403 with no switch, and Q5's "all on for Smart Logistics"
had no mechanism behind it.

This is 9110's own documented failure mode a second time. Its header records the
first: "nine keys below were flipped 'off' -> 'on' because their modules are
built and mounted, and leaving them off made 19 modules unreachable for
everyone." Same shape, fifteen different keys — and worse, because a missing
catalogue row cannot even be seen in the console, let alone flipped.

Seed 9113 adds all fifteen under MOD-64, hung off `comms` so turning Smart Comms
off takes the mailbox with it. Twelve default ON: 9110 is explicit that
default_state answers "is this module SHIPPABLE?", not "did the customer buy
it?", and plan inclusion is the commercial gate. Three default OFF for reasons
that are not readiness — mail.ai (opt-in like every ai.* key, and naming
ai.assistant.backend in depends_on moves §3.3's floor-not-ceiling rule into the
projection itself), mail.ocr (a vision vendor, billed per page), and
mail.provider.oauth (Graph and Gmail are built and deliberately gated).

feature-catalogue-coverage fails when a tenant-seeded flag has no catalogue row,
when a depends_on names a key the catalogue lacks — the projection treats an
unknown dependency as unmet and forces the feature off to a fixpoint, so a typo
there silently turns a shipped feature off for every tenant — or when the
dependency graph has a cycle.

Twenty-three endpoints had no interface
----------------------------------------
Four new tabs in /comms/setup: follow-ups, secure links, response times (SLA
policies plus working hours and holidays), and trust & archive (confirmed
domains, bounces, chain verification).

The gating came from what the server returns, not from how administrative each
felt. workflow.listFollowups filters on `f.user_id = $1`, so that list is the
caller's own and everyone gets it. secure-link.list has no created_by filter —
it is every link in the tenant and the labels name clients and invoices — so it
is admin-only for that reason.

Also wired: per-thread sharing beside the visibility control, and the composer's
secure-link offer. That last had been a caption reading "Sending a secure link
instead arrives in a later release", sitting above a SECURE_LINK_HINT_BYTES
threshold outbox.service had computed since PR-1B. It arrived with PR-5 and the
caption stayed — worse than never promising it, because the operator reads it,
believes the feature is missing, and attaches the 18 MB PDF anyway. The button
now mints the link, drops it into the body and detaches the file; doing only the
first would send both.

What the screens had to carry
------------------------------
Rules the API cannot enforce on its own, so setup-pr5.test.tsx pins them: a
secure-link token is shown ONCE (only its SHA-256 is stored, so if the dialog
does not say so the operator loses it with no error to explain why); an OBSERVED
domain is not a verified one (an impostor who emails twice is observed twice,
and the whole anti-spoof control rests on that distinction); with nothing
confirmed the send block stops nothing, said on the screen because an absent
warning reads as safety; a broken hash chain is usually concurrency rather than
tampering but the consequence for evidence is identical; and no SLA policy is a
valid answer, not a misconfiguration to nag about.

Two defects in this programme's own commits
--------------------------------------------
work.test.tsx shipped `import * as React` under noUnusedLocals, which fails
`tsc -b` — the first half of npm run build. It passed review because vitest
transpiles without typechecking, so a green test run says nothing about whether
the client compiles.

And the new tests asserted against half the DOM: DataList renders every row
twice, a table and a card list with one hidden by CSS, and jsdom applies no
stylesheet.

5,126 backend tests across 334 suites, 0 lint errors, column/idempotency/citext
OK. Client typecheck clean, 1,649 vitest tests passing.
